# 第三轮风险分析（第一性原理）

分析范围：`SearchService.java`（2348行）、`DocImportController.java`（559行）

---

## A 类：安全漏洞

### A-1 GRANT 权限检查仍依赖 ES metadata.granted_users — P0（安全绕过）

**根因：** `SearchService.java:748` 中 GRANT 权限过滤仍用 ES `metadata.granted_users` 字段：
```java
permBool.should(bGrant.must(m1.term("metadata.visibility", "GRANT"))
                       .must(m2.term("metadata.granted_users", userId)));
```
但上一轮 P0-5 已将 GRANT 权限的**管理端权威来源**迁移到 MySQL `kb_doc_grants` 表。两套数据可能不一致：
- 若 MySQL 中已撤销授权，但 ES 字段未更新 → 用户仍能搜到本应无权的文档
- 若 MySQL 中已授权，ES 未更新 → 用户无法搜到本应可见的文档

**修复：** 搜索层 GRANT 过滤需改为两阶段策略：
1. ES 过滤层：增加 `metadata.visibility = GRANT` 过滤（只拉取 GRANT 类文档候选）
2. Java 层后过滤：对 GRANT 候选文档调用 `KbDocGrantsService.checkAccess` 做 MySQL 二次权限校验，过滤掉 ES 与 MySQL 不一致的条目

### A-2 batch_import/sftp_import/url_import 三个接口无鉴权 — P0

**根因：**
- `/admin/doc/batch_import`（L64）：任何人可调用，传入任意服务器路径（如 `/etc`），触发遍历读取
- `/admin/doc/sftp_import`（L362）：无鉴权，且接收明文密码 `pass` 字段
- `/admin/doc/url_import`（L418）：无鉴权

三个接口均在 `/api/v1/admin/` 前缀下但没有 `permissionGuard.isValidInternalToken()` 校验，而同文件中的 `taskCallback`、`listBatches`、`listTasks` 已经加了鉴权，形成鉴权不一致。

**修复：**
```java
// batch_import 入口处加
if (!permissionGuard.isValidInternalToken(httpRequest.getHeader("X-Internal-Token"))) {
    return unauthorized();
}
```

### A-3 URL 下载接口 SSRF — P0

**根因：** `url_import:427` 直接 `new URL(fileUrl).openStream()`，没有任何 URL 白名单或協议检查。攻击者可传入：
- `file:///etc/passwd` → 读取服务器本地文件
- `http://169.254.169.254/latest/meta-data/` → 获取云服务器 IAM 凭据（SSRF）
- `http://internal-service:8080/admin` → 探测内网服务

**修复：**
```java
// URL 白名单校验（协议 + 域名）
private static final List<String> ALLOWED_URL_PREFIXES = List.of("https://", "http://docs.");

private void validateUrl(String url) {
    URI uri = new URI(url);
    String scheme = uri.getScheme();
    if (!"http".equals(scheme) && !"https".equals(scheme))
        throw new IllegalArgumentException("不支持的协议: " + scheme);
    String host = uri.getHost();
    if (isPrivateIp(host))
        throw new IllegalArgumentException("禁止访问内网地址: " + host);
}
```

### A-4 SFTP 接口明文密码传输 — P1

**根因：** `sftp_import:367` 从请求体直接读取 `pass` 字段：
```java
String pass = request.get("pass");
new SftpUtil(host, port, user, pass)
```
密码以明文 JSON 在 HTTP Body 中传输，且会被完整记录到日志中（若开启 request body logging）。

**修复：** SFTP 凭证应通过预配置的 Credential Store（如 Vault、环境变量）管理，接口只接受 `credentialId`，不直接接收密码。

---

### A-5 Pre-Flight 快速路径无权限过滤 — P0（权限绕过）

**根因：** `SearchService:516-564` Pre-Flight Probe 检索时的 ES filter 未包含权限过滤（只有 `is_latest` 过滤），若精确匹配命中，直接返回文档内容而不经过权限校验：
```java
// Pre-Flight 的 filter 块：
b.filter(f -> f.bool(boolQuery -> boolQuery
    .should(s -> s.term("metadata.is_latest", true))
    ...
));
// 没有 visibility / uploader_id / granted_users 权限过滤！
```
攻击者输入文档标题即可绕过权限访问任意文档。

**修复：** Pre-Flight 请求 builder 中复用主查询的权限过滤构建器（提取为 `buildPermissionFilter(userId, isAnonymous, deptAncestorValues)` 方法），确保所有路径都经过相同权限过滤。

---

### A-6 存量文档 visibility 字段缺失时自动放行 — P1（隐式权限扩大）

**根因：** `SearchService:723-736` 对登录用户和匿名用户，`visibility` 字段不存在时均通过 `mustNot.exists` 放行：
```java
// 存量文档字段缺失 → 视为 INTERNAL 放行（登录用户）
permBool.should(s -> s.bool(bNot -> bNot.mustNot(mn -> mn.exists(field("metadata.visibility")))));
```
此兼容逻辑导致所有无 `visibility` 字段的历史文档对任意登录用户可见，包括本应是 PRIVATE 或 DEPT 的文档。

**修复：** 对存量文档执行一次性数据修复脚本，将缺失 visibility 的文档置为 `INTERNAL`，并在修复完成后移除该放行逻辑。

## B 类：数据一致性

### B-1 content_hash 仅取前 8KB → 大文件重复检测失效 — P1

**根因：** `DocImportController:547` `computeContentHash` 只 hash 前 8KB，两个内容不同但前 8KB 相同的大文件（如同一模板填充不同数据）会被视为重复而跳过

**修复：** 对完整文件计算哈希（或至少取末尾 8KB 与首部 8KB 拼接哈希），避免假阳性去重。

---

## C 类：性能与资源

### C-1 SearchService 多处 new RestTemplate / new ObjectMapper — P1

**根因：**
- `fetchRewriteAndHyde:151`：`new RestTemplate()`
- `fetchLlmRerankScores:326`：`new RestTemplate()`
- `fetchQueryVector:378`：`new ObjectMapper()`（`normalizeQuery:207` 也有）
- `fetchColbertScores:290`：`new ObjectMapper()`

每次搜索请求都创建这些重量级对象，导致显著 GC 压力（`RestTemplate` 包含连接池、序列化器等）。

**修复：** 将 `llmRestTemplate` 和 `mergedRestTemplate` 提升为类成员（与已有的 `this.restTemplate` 相同模式），ObjectMapper 注入全局 Bean。

---

### C-2 DocImportController.createTasks 每次 new ObjectMapper — P1

**根因：** `createTasks:495`：`new ObjectMapper()` 在每个任务 payload 序列化时创建，若一次批量导入100个文件，创建100次。

**修复：** 注入 `ObjectMapper` Bean：`@Autowired ObjectMapper objectMapper;`

---

### C-3 Semaphore 并发 COLBERT_SEMAPHORE 未在超时后释放 — P2

**根因：** `SearchService:102` `COLBERT_SEMAPHORE` 是类级 `static final`，但扫描代码中未看到显式的 `tryAcquire → ... → release` Try-Finally 模式，若 ColBERT 调用过程中发生异常，Semaphore 许可可能不被释放，导致逐渐耗尽直至所有请求降级。

**修复：** 使用 Try-Finally 确保 release：
```java
if (COLBERT_SEMAPHORE.tryAcquire(100, TimeUnit.MILLISECONDS)) {
    try {
        scores = fetchColbertScores(query, docs);
    } finally {
        COLBERT_SEMAPHORE.release();
    }
}
```

## D 类：运维与可观测性

### D-1 SearchService @PostConstruct 在启动时执行 DDL — P2

**根因：** `SearchService:60` 在 Spring Bean 初始化时执行 `ALTER TABLE` DDL，不符合"代码与 Schema 分离"原则。若多节点部署（水平扩展），每个节点启动都会竞争执行 DDL，可能引发并发冲突。此外 DDL 失败会打印到 stdout 而非走结构化日志。

**修复：** DDL 迁移统一由 `DbInitRunner`（已存在）负责，从 `SearchService` 中移除。
