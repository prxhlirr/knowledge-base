# 知识库项目生产化前置修复与 5000+ 并发实施计划

> 文档版本：v1.0  
> 文档状态：待范围评审  
> 适用项目：`knowledge-base`  
> 目标：由当前开发/受控试运行状态，演进为可验证、可恢复、可扩展的生产系统  
> 执行原则：先保证安全与数据正确性，再保证稳定性与容量，最后优化高级 AI 能力

---

## 1. 文档目的

本计划用于完成以下工作：

1. 将此前发现的文档解析、分片、向量化、入库、权限、检索、问答和基础设施问题转化为可执行任务。
2. 明确哪些任务是生产上线阻断项，哪些任务是 5000+ 并发目标的前置项，哪些任务可以延期。
3. 为每个工作包定义改造范围、涉及目录、依赖关系、验收标准、预期效果和延期风险。
4. 用户评审并选择工作包后，严格按照批准顺序逐项实施、测试和验收。

本文不代表所有事项已获批准。所有标记为 `待决策` 的工作包，必须由用户选择后才能进入代码实施阶段。

## 2. 第一性原理与生产不变量

本项目的核心目标不是“把文件转成 Markdown”或“生成向量”，而是：

> 让用户在权限范围内，快速找到最新、正确、可追溯的知识，并基于可靠证据获得答案。

生产环境必须满足以下六个不变量：

1. **不越权**：任何索引、缓存、QA、相似度和历史版本都不能绕过权限过滤。
2. **不丢任务**：任何已接受的导入任务都必须有持久化事实记录，能够恢复、重试或进入死信。
3. **不静默丢内容**：解析不完整、OCR 低置信度或结构缺失必须显式标记，不能伪装成完整文档发布。
4. **不混用版本**：文档、解析器、分片器、向量模型、索引 Schema 和权限都必须版本化。
5. **不让局部故障拖垮全站**：OCR、入库、Rerank、LLM 等非核心能力故障时，关键词检索仍应可用。
6. **可追溯、可恢复**：任何结果都能追溯到原文件和原始证据，任何关键存储都完成实际恢复演练。

## 3. 范围决策说明

### 3.1 优先级定义

| 级别 | 含义 | 延期原则 |
|---|---|---|
| P0 | 生产上线阻断项 | 原则上不得延期；延期必须书面接受风险并缩小上线范围 |
| P1 | 达成 5000+ 在线用户和高并发目标的必要项 | 可在小流量试运行后完成，但不得在正式扩容前缺失 |
| P2 | 高保真、成本优化和长期治理项 | 可分阶段实施，但应保留接口和数据模型扩展空间 |

### 3.2 决策状态

评审时将每个工作包的状态修改为以下之一：

- `批准`：进入执行队列。
- `延期`：当前不执行，记录延期风险和重新评审时间。
- `拒绝`：明确不纳入当前产品范围。
- `待调研`：需要先执行只读验证或 PoC。
- `待决策`：默认状态。

### 3.3 待用户确认的容量口径

| 决策项 | 推荐基线 | 当前状态 |
|---|---|---|
| 5000+ 的定义 | 5000 在线用户/连接，不等于 5000 路同时生成答案 | 待决策 |
| 搜索峰值 | 100～300 QPS，压测扩展到 500 QPS | 待决策 |
| Keyword P95 | 不高于 800ms | 待决策 |
| Hybrid P95 | 不高于 2s | 待决策 |
| Hybrid P99 | 不高于 3～5s | 待决策 |

| 同时 LLM 生成数 | 按 GPU 实测容量限制，初始建议 8～32 | 待决策 |
| 数据规模 | 明确文档数、Chunk 数、年增量、单文档平均大小 | 待补充 |
| OFD | 正式支持，或明确返回 415 不支持 | 待决策 |
| 高保真范围 | 是否包含复杂表格、图片 OCR、公式、修订、脚注和页码引用 | 待决策 |
| 部署平台 | 多虚拟机或 Kubernetes | 待决策 |

## 4. 目标架构

```text
用户
  ↓
双实例负载均衡 / Nginx
  ↓
Java 在线服务集群（无状态）
  ├── Keyword Search
  ├── Hybrid Search
  ├── Permission Guard
  └── QA Evidence Gateway
       │
       ├── Redis Cache 集群
       ├── Elasticsearch 集群
       └── AI 在线推理层
              ├── Embedding 实例池
              ├── Rerank 实例池
              └── LLM 推理实例池

文档接入
  ↓
Java Ingest Service
  ↓
PostgreSQL Task/Outbox + 持久化任务队列
  ↓
离线 Worker 层
  ├── Document Parser Worker
  ├── OCR Worker
  ├── Chunk/Embedding Worker
  └── Index Publisher Worker
       │
       ├── MinIO 原始文件与解析产物
       ├── PostgreSQL 元数据、任务、权限、版本
       └── Elasticsearch 暂存索引与正式索引
```

设计边界：

- Java 继续负责业务、身份、权限、版本、任务事实和搜索编排。
- Python 继续负责解析、OCR、分片和模型推理。
- 不立即新建独立代码仓库；优先在 `ai_service` 内模块化，通过不同启动入口独立部署。
- 文档处理不得与在线推理共享进程和并发池。
- LLM 是可降级能力，不能成为关键词检索的强依赖。

## Phase 2：任务可靠性与服务隔离

### PR-0201 Redis缓存与任务队列拆分

- 优先级：P0
- 决策状态：待决策
- 工作内容：
  - 缓存Redis保留 `allkeys-lru`。
  - 任务Redis使用 `noeviction`、AOF、主从和故障转移。
  - 队列、重试、DLQ、回调补偿、幂等键全部迁移到任务Redis。
  - 设置队列深度、AOF延迟、内存和淘汰告警。
- 验收标准：缓存Redis清空或爆满时，任务不丢失；任务Redis重启后队列可恢复。
- 预期效果：消除缓存策略误伤关键任务的风险。

### PR-0202 统一任务状态机与租约

- 优先级：P0
- 决策状态：待决策
- 目标状态：
  - `PENDING`
  - `QUEUED`
  - `RUNNING`
  - `RETRYING`
  - `STAGED`
  - `SUCCESS`
  - `FAILED`
  - `QUARANTINED`
  - `DEAD_LETTER`
- 工作内容：
  - PostgreSQL作为任务事实源。
  - Worker领取任务时写入租约、owner和heartbeat。
  - 超时租约可由恢复任务重新入队。
  - taskId、文件Hash、文档版本共同保证幂等。
  - 重试使用指数退避和最大次数。
- 测试：Worker执行中崩溃、重复消息、回调超时、Redis重启、Java重启。
- 验收标准：任务最终收敛到明确终态，无永久RUNNING和重复发布。

### PR-0203 在线AI与文档Worker分离

- 优先级：P0
- 决策状态：待决策

  - 在线实例和Worker使用独立CPU、GPU、内存和并发限制。
  - OCR、解析、入库失败不得影响Embedding健康检查。
- 验收标准：大文件/OCR压测期间，在线搜索延迟不显著劣化。

### PR-0204 入库任务后台治理界面

- 优先级：P1
