# 博杨 AI 检索架构：模型调优参数权威白皮书

在经过深度的代码倒查与链路剖析后，原有的 7 个因为系统底层 GPU自适应升级、逻辑剥离而失效的**“空转参数”** (安慰剂参数，如 `device`, `truthfulUiCeiling` 等) 已被全部彻底铲除。

以下为当前系统中**绝对真实、可靠、可实时热调优**的**15项核心参数**。每一项都深深扎根于底层的 Java 调度机制与 Python 算力控制中，任何调整都将立即改变搜索的形态。

---

## 模块一：核心策略与算力约束配置

### 1. CPU 线程数 (`cpuThreads`)
- **调整策略**：如果在无 GPU 环境下迫降纯 CPU 推断计算，或使用 `CPUExecutionProvider` 时，此值决定了底层 ONNX 开启的并行计算线程数。
- **改善方向**：改善高并发下的吞吐量。若一味调大可能导致服务器 CPU 100% 抢锁死锁；若调得太小则运算耗时无限拉长。
- **实例支撑**：一台 8 核 16 线程服务器，调至 `12` 可以兼顾 AI 并发处理与操作系统运行；调至 `32` 则会导致所有 Web 请求和 ES 查询被挤占而致使容器宕机崩溃。

### 2. 传统文本基准权重比 (`bm25Weight`) & 向量权重比 (`vectorWeight`)
- **调整策略**：此参数控制 **RRF（排位倒数融合算法）**在双轨召回后的票仓归属。当发现系统“过分理解但找不准原话”时调高 BM25；当发现“同义词搜不出来”时调高 Vector。
- **实例支撑**：用户搜索“2023 员工规章手册”。这极度依赖字面上的精确数字和词元。若 `vectorWeight` 设置为 0.9，排在第一的可能是通篇讲“团队纪律规定”（语义相似）的无用文章；此时将其下修至 `0.4`，将 `bm25Weight` 拔高至 `0.6`，那篇名为《2023年员工规章》的原文件将瞬间凭借强词元抢回第一名。

### 3. RRF 排序探测窗口 (`rrfWindowSize`)
- **调整策略**：两路召回结果进入排行榜评比的最大板凳深度。如果文档库极大且长尾质量很差，应该缩小窗口以节约内存。
- **改善方向**：改善深水区极弱相关文档（垫底文档）意外凭借两侧微弱评分合谋上位的问题。
- **实例支撑**：默认是 `60`。若设为 `200`，字面召回第 180 名的垃圾文档和向量召回第 190 名的垃圾文档极有可能会合并出一个中等偏上的总排位进入重排浪费显卡。收窄至 `60` 可以掐断尾部垃圾的晋升阶梯。

### 4. 标题匹配优先级权重 (`titleBoost`)
- **调整策略**：控制 ES 全文检索语句中的 `metadata.source^N` 的 N 乘数放大倍率。
- **实例支撑**：输入“安全准则”。有一篇文档名为《企业管理》，内容出现 50 次“安全准则”；另一篇名为《安全准则必读》，内容只有 1 次“安全准则”。如果 `titleBoost` 是 1.0，前者可能得分更高。如果 `titleBoost` 调为 `15.0`，后者凭借标题中签，将无悬念吊打前者霸榜召回第一。

### 5. ES 原生分数分母惩罚基准 (`esNormBase`)
- **调整策略**：全文检索匹配分 (基于 BM25 算法) 从 0 无上限，要与向量余弦距 (0~1) 融合，必须做除以惩罚项的衰缩。
- **实例支撑**：如果发现您的 Elasticsearch 文档特别长、出现频率极高导致打分经常溢出到 50 分以上，此时调大 `esNormBase` (例如调大至 `100.0`) 将粗暴压制 BM25 畸形高分，使两端归一化处于同样一个数量级内。

## 模块二：精排算力控制与时延换血 (Latency/Accuracy Trade-off)

### 6. 精排池极限截流文档数 (`rerankLimit`)
- **调整策略**：从初赛进入复赛（Cross-Encoder 重排）的最大人数。这是最吃显卡算力的环节。它呈绝对线性相关：每多 1 篇，延迟多 5~10 毫秒。
- **改善方向**：在精准度和高延迟之间做生死抉择。
- **实例支撑**：如果调优为 `5`，系统极其丝滑（总体耗时仅需 30ms），但第 6 篇本来更好的文档被永远埋没。如果调优为 `80`，你可以非常精准地把第 78 篇珍宝打捞回第一，但你的单次搜索代价可能突破 `800ms`。

### 7. 单文过审精排截断长度 (`rerankMaxChars`)
- **调整策略**：单篇文档在送进 Cross-Encoder 黑盒前，保留的最大字串数。长句导致内存 `O(n^2)` 爆炸。
- **实例支撑**：如果你关注的是“全文内容细节匹配”，将此值调至 `1000` 可以防止由于关键词藏在长文末尾而被截去；如果你只关心文件头部总则，将其调小至 `300` 可使得每次 Rerank 节省下 70% 的显存与计算耗时。

## 模块三：通信熔断与防系统性雪崩 (Timeouts/Breakers)

### 8. ES 底座检索超时封锁 (`esQueryTimeout`)
- **作用**：控制 Java 等待 ElasticSearch 吐网包的最长硬容忍毫秒级别。
- **实例**：面对疯狂扫表或者极其生僻的长文全匹配，ES可能假死锁死。此值调为 `800`，意味着只要 800 毫秒没出来结果，Java 直接拉闸报障，防止线程池被耗尽导致后续几十名用户也打不开网页。

### 9. 向量提取 (`embeddingTimeout`) 与 交叉比对 (`rerankTimeout`) 超时
- **作用**：与 Python 算力服务的 HTTP 超时。
- **实例**：如果显卡突然显存溢出 OOM 或任务卡壳阻塞，`rerankTimeout` 设置为 `2000` 将在那篇破文档卡了足足 2 秒后，毫不留情地切断链接，保护整个 Java JVM 生命周期。

## 模块四：黑客与核武器级别防线 (Extreme Heuristics)

### 10. 纯词汇提速通道拦截长度 (`lexicalFastPathMaxLength`)
- **调整策略**：设置多短的词**不走**大模型！
- **实例**：配置为 `2`。当用户搜索“消防”二字时，没必要通过巨大矩阵计算“消防”的隐含语义，直接跳过 AI 交给字面 ES 去拉取，全链路耗时瞬间从两百毫秒降至不到 20ms。

### 11. 宽视野免排阈值 (`adaptiveBreakerMaxLength`)
- **调整策略**：如果词语也不长，语义过于空泛（例如“报告总结”），此时交叉重排很难有绝对胜负，还白白交过路费。
- **实例**：配置为 `4`。搜索“2023工作”（长 6 字符。不拦截，乖乖重排）；搜索“放假规定”（长 4 字符。拦截重排，因为大家都讲这个，怎么排都是一样的，干脆只拼字库命中）。

### 12. 底线放弃：最低 RRF & 原始分 (`breakerRrfThreshold` & `breakerRawScoreThreshold`)
- **调整策略**：这关乎“强扭的瓜有多苦”。
- **实例**：用户搜索极偏门的“爱马仕保养”。库里根本没有！但是由于 KNN 是计算距离的，它一定会强行返回一个距离十万八里远的“马达保养规程”。此时 RRF 非常低（比如由于分数低只得了 0.012），未摸到 `0.020` 的底线阈值。系统判定：没有相关玩意，断掉后续模型开销。

### 13. [核武] 高分碾压直通车 (`highScoreExemptionThreshold`)
- **调整策略**：对付最常见且最确定的搜寻！
- **改善方向**：避免把显而易见的黄金结果扔给机器重新做漫长的质检。
- **实例支撑**：配置为 `12.0`。用户正好搜索《国务院火灾防控指导办法》。ES 里面恰好就有一篇叫一模一样名字的文档。此时 ES 计算出来的分数极高，达到了 `28.5` 远超 `12.0`。这个时候，Java 层拍碎了红灯，惊呼：“就是它了！满门抄斩其他候选集！”随即颁发**免重排金牌**，跳过了那 8S 延迟噩梦，以不到 `50ms` 的神速推送给了用户！
