# 第二轮风险分析（第一性原理）

分析范围：DocTaskRecoveryJob、DocPermissionService、CorsConfig、ElasticSearchConfig、MinioStorageService、SearchCacheService、SftpUtil、task_worker.py、Admin.vue

---

## A 类：安全漏洞

### A-1 CORS allowedOrigins("*") — P0

**根因：** 允许任意来源跨域，攻击者可构造恶意页面借用用户浏览器发起 CSRF，删除文档或触发管理操作。

```java
// 修复：CorsConfig.java 改为白名单
@Value("${cors.allowed-origins:http://localhost:5173}")
private String origins;

registry.addMapping("/**")
    .allowedOriginPatterns(origins.split(","))
    .allowedMethods("GET","POST","PUT","DELETE","OPTIONS")
    .allowedHeaders("*").maxAge(3600);

// application.yml
cors.allowed-origins: http://localhost:5173
```

---

### A-2 SftpUtil 禁用主机密钥校验 — P0

**根因：** `StrictHostKeyChecking = no` 信任任何中间人，攻击者可 MITM 劫持 SFTP 通道盗取文档内容。

```java
// 修复：使用 known_hosts 文件
@Value("${sftp.known-hosts:/etc/ssh/known_hosts}")
private String knownHostsPath;

jsch.setKnownHosts(knownHostsPath);
// 删除 config.put("StrictHostKeyChecking", "no")
```

---

### A-3 task_worker 回调无 X-Internal-Token — P0（功能断裂）

**根因：** `post_callback()` 发送到 `/internal/task/callback` 时未携带 `X-Internal-Token`，而 P2-3 已在 Java 端加了 Token 校验。结果：**所有回调返回 401，任务状态永远停在 PENDING 无法变为 INDEXED**。这是目前最紧急的功能断裂。

```python
# 修复：task_worker.py
INTERNAL_TOKEN = os.getenv("KB_INTERNAL_TOKEN", "kb-dev-token-change-me-in-prod")

def post_callback(task_id: str, status: str, error_msg: str):
    headers = {
        "Content-Type": "application/json",
        "X-Internal-Token": INTERNAL_TOKEN
    }
    req = urllib.request.Request(url, data=data, headers=headers)
    with urllib.request.urlopen(req, timeout=5) as resp:
        body = resp.read().decode()
        if resp.getcode() != 200:
            raise RuntimeError(f"Callback rejected HTTP {resp.getcode()}: {body}")
```

### A-4 task_worker 日志接口明文 Token — P1

**根因：** `"token": "bge_secret_token_123"` 硬编码在 `post_log_report()` 中，与 KB_INTERNAL_TOKEN 体系脱节。

**修复：** `"token": os.getenv("KB_INTERNAL_TOKEN", "")`

### A-5 ElasticSearchConfig 无 Basic Auth — P1

**根因：** `RestClient.builder(new HttpHost(host, port, "http"))` 无认证，ES 依赖网络隔离，隔离失效即完全暴露。

```java
// 修复：ElasticSearchConfig.java
@Value("${elasticsearch.username:}") private String esUsername;
@Value("${elasticsearch.password:}") private String esPassword;

RestClientBuilder builder = RestClient.builder(new HttpHost(host, port, "http"));
if (esUsername != null && !esUsername.isEmpty()) {
    CredentialsProvider cp = new BasicCredentialsProvider();
    cp.setCredentials(AuthScope.ANY,
        new UsernamePasswordCredentials(esUsername, esPassword));
    builder.setHttpClientConfigCallback(b -> b.setDefaultCredentialsProvider(cp));
}
```

## B 类：数据一致性风险

### B-1 幂等删除先于入库：崩溃永久丢数据 — P1

**根因：** `task_worker.py` 第73行 `delete_by_query` 在 `process_and_index()` 之前执行。若入库期间崩溃（OOM/文件损坏），历史版本已删、新版本未写入，**文档在 ES 中永久消失**。

**修复（蓝绿写入模式）：**
```
旧流程：delete_by_query → process_and_index（先删再写，有数据窗口）
新流程：
  1. process_and_index 写入新版本（is_latest=true，version=N）
  2. 写入成功后，update_by_query 将旧版本置 is_latest=false
  3. 崩溃时旧版本数据完整保留，可继续搜索
```

---

### B-2 可见度变更 ES/MySQL 双写无事务 — P0（安全+一致性）

**根因：** `DocPermissionService.addVisibilityChange()` 内，MySQL 写入在 `@Transactional` 保护下，ES 更新在 try/catch 内但事务已提交。ES 失败时 MySQL 说"已变更"，但搜索层的 ES 仍用旧 visibility 过滤，**文档被降权但用户仍能搜到**。

**修复（补偿队列）：**
```java
// ES 更新失败时，写入 es_sync_pending 补偿表
// 新增 EsSyncRetryJob 每分钟消费，重试直至 ES 一致
// es_sync_pending 表：(id, doc_source, update_type, payload, retry_count, created_at)
```

---

### B-3 RecoveryJob 重推 visibility 硬编码为 INTERNAL — P1

**根因：** `DocTaskRecoveryJob.java:129` 恢复任务时 payload 里 `"visibility": "INTERNAL"` 写死，原任务若为 DEPT/PRIVATE/GRANT，则恢复入库后权限被静默**扩大为 INTERNAL**，任何已登录用户均可访问。

**修复：** `sys_doc_import_task` 表增加 `visibility`、`dept_code` 列，建入库时存原始值，恢复时从库中读取。

## C 类：性能与资源

### C-1 SearchCacheService 使用 KEYS 全量扫描阻塞 Redis — P1

**根因：** `redisTemplate.keys("search:cache:*")` 是阻塞命令，Redis 单线程执行期间所有其他命令排队等待。生产环境 Redis 万级 key 时可能阻塞数百毫秒。

```java
// 修复：SCAN 游标替代 KEYS
ScanOptions opts = ScanOptions.scanOptions()
    .match(KEY_PREFIX + "*").count(100).build();
try (Cursor<String> cursor = redisTemplate.scan(opts)) {
    while (cursor.hasNext()) {
        String key = cursor.next();
        String val = redisTemplate.opsForValue().get(key);
        if (val != null && val.contains(docSource)) {
            redisTemplate.delete(key);
        }
    }
}
```

---

### C-2 DocTaskRecoveryJob 每次 new ObjectMapper — P3

**根因：** 每次重推任务 `new ObjectMapper()`，ObjectMapper 是重量级对象，不必要地消耗 CPU 和内存。

**修复：** 注入 Spring 单例 Bean：`@Autowired ObjectMapper objectMapper;`

## D 类：运维与可观测性

### D-1 MinioStorageService 硬编码桌面路径 — P0（部署即失效）

**根因：** `private String localPath = "C:\\Users\\liyz\\Desktop\\tmp"` 是开发者本地路径，任何其他机器部署时文件上传直接报 IOException。

```java
// 修复：MinioStorageService.java
@Value("${storage.local.path:${java.io.tmpdir}/kb-uploads}")
private String localPath;

// application.yml 新增
storage:
  local:
    path: /data/kb-uploads   # 生产路径
```

---

### D-2 Admin 仪表盘硬编码假数据 — P2

**根因：** "今日搜索次数: 64" 写死在 `Admin.vue` 模板，仪表盘不反映真实系统状态，运维据此做出错误判断。

**修复：** 新增 `/api/v1/admin/stats` 接口，从 Redis `search:query_log` 统计今日条数，从 ES `/_cluster/health` 获取集群状态，前端 `onMounted` 拉取。
