# 知识库项目 — 第一性原理风险分析报告

> 分析范围：文档导入（rag_pipeline.py）、权限管理（PermissionGuard.java + 相关 Controller）、混合检索（SearchController.java + SearchService.java）  
> 分析方法：从每个模块的**根本职责**出发，追溯每一个隐患的数据流根源，给出可闭环的根治方案。

## 一、文档导入（Document Ingestion）

### 🔴 风险 I-1：内部回调 Token 硬编码明文泄露

**根本原因（First Principles）**  
`PermissionGuard.java` 第 41 行：
```java
private static final String INTERNAL_TOKEN_VALUE = "kb-internal-rpc-token";
```
凭证直接写在源代码中，一旦代码库泄露（Git 历史、反编译 jar、日志截图），内部凭证即时失效。攻击者可直接伪造 Python → Java 的 `/internal/doc/registry` 回调，注入任意文档元数据（篡改 visibility、uploader、版本号）。

**风险等级**：🔴 高（数据完整性 + 权限越权）

**根治方案**

```
1. 将凭证迁移到配置中心/环境变量：
   application-prod.yml:
     internal:
       token: ${KB_INTERNAL_TOKEN:#{null}}
   并在 PermissionGuard 注入：
     @Value("${internal.token}") private String internalTokenValue;

2. 生产禁用 null 值：启动时 @PostConstruct 校验 internalTokenValue 非空，否则拒绝启动。

3. 长远替代方案：内服务间改用 mTLS 双向证书，网关层颁发短期 JWT token（ttl=5min），
   彻底消除静态密钥的攻击面。
```

### 🔴 风险 I-2：文件路径硬编码（MODEL_PATH / ES_HOST）

**根本原因**  
`rag_pipeline.py` 第 20-21 行：
```python
MODEL_PATH = r"E:\project\AI\knowledge-base\models\bge-m3"
ES_HOST = "http://localhost:9200"
```
绝对路径绑定开发机，生产/容器化环境部署直接失败（无法自动发现）；ES 以 HTTP 明文暴露，无认证。

**风险等级**：🟠 中（部署安全 + 可移植性）

**根治方案**

```python
# 改为环境变量 + 默认值兜底模式
import os
MODEL_PATH = os.getenv("MODEL_PATH", "./models/bge-m3")
ES_HOST    = os.getenv("ES_HOST", "http://localhost:9200")
ES_USER    = os.getenv("ES_USER", "")
ES_PASS    = os.getenv("ES_PASS", "")

# ES 客户端加入 Basic Auth
self.es = Elasticsearch(
    ES_HOST,
    http_auth=(ES_USER, ES_PASS) if ES_USER else None,
    scheme="https" if ES_HOST.startswith("https") else "http"
)
```
并在 `docker-compose.yml` / `.env` 文件中统一管理，`.env` 加入 `.gitignore`。

### 🔴 风险 I-3：文件上传无类型/大小限制 → 恶意文件 & DoS

**根本原因**  
`rag_pipeline.py` `extract_text()` 接受任意 `file_path`，上层 AI Service（`main.py`）的上传接口未见文件类型白名单和大小上限校验。即使有前端过滤，绕过前端的直接 HTTP 请求仍可上传：
- `.exe`/`.bat` 伪装为 `.docx`（MIME Spoofing）
- 超大 PDF/DOC（数百 MB）耗尽内存和 GPU
- 恶意 zip bombs（伪装成 docx 的 xml 压缩包）

**风险等级**：🔴 高（DoS + 远程代码执行风险）

**根治方案**

```python
# 在 task_worker.py / main.py 的上传入口添加防护层
ALLOWED_EXTENSIONS = {'.pdf', '.docx', '.doc', '.xlsx', '.pptx', '.txt', '.md'}
MAX_FILE_SIZE_BYTES = 50 * 1024 * 1024  # 50MB

def validate_file(file_path: str, file_size: int):
    ext = os.path.splitext(file_path)[1].lower()
    if ext not in ALLOWED_EXTENSIONS:
        raise ValueError(f"不支持的文件类型: {ext}")
    if file_size > MAX_FILE_SIZE_BYTES:
        raise ValueError(f"文件大小超限: {file_size / 1024 / 1024:.1f}MB > 50MB")
    # 魔术字节校验（不信任扩展名）
    magic_map = {'.pdf': b'%PDF', '.docx': b'PK\x03\x04', '.doc': b'\xd0\xcf\x11\xe0'}
    with open(file_path, 'rb') as f:
        header = f.read(4)
    if ext in magic_map and not header.startswith(magic_map[ext]):
        raise ValueError(f"文件魔术字节不匹配，怀疑伪造扩展名")
```

### 🟠 风险 I-4：内容哈希去重仅取前 2000 字 → 伪去重

**根本原因**  
```python
raw_sample = (raw_text or "")[:2000]
content_hash = hashlib.md5(raw_sample.encode(...)).hexdigest()
```
MD5 碰撞不安全；仅哈希前 2000 字时，不同正文但相同序言的文档会被错误识别为重复（漏入库）；MD5 本身有已知碰撞攻击，选型过时。

**风险等级**：🟠 中（数据完整性、漏入库）

**根治方案**

```python
import hashlib

# 对全文本计算 SHA-256，不截断
def compute_content_hash(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8", errors="ignore")).hexdigest()

content_hash = compute_content_hash(raw_text or "")
```
同时在 `kb_doc_meta` 的 ES Mapping 和 MySQL `kb_doc_registry` 中，给 `content_hash` 字段建唯一约束（ES term aggregation + MySQL UNIQUE KEY），才能真正闭环去重。

### 🟠 风险 I-5：版本号并发竞争（TOCTOU Race Condition）

**根本原因**  
`_get_next_version()` 从 ES 读最大版本号后 +1，但存在**读-计算-写**非原子操作窗口。并发上传同名文档时，两个进程可能读到相同的 `max_ver`，写入相同版本号，导致版本覆盖。

**根治方案**

```
方案 A（推荐）：版本号迁移到 MySQL，利用数据库的行锁或乐观锁。
  - kb_doc_registry 新增 current_version 字段
  - UPDATE kb_doc_registry SET current_version=current_version+1 WHERE source_name=? 
    RETURNING current_version（原子自增，事务保证）

方案 B：Redis 原子计数器
  new_version = redis.incr(f"doc:version:{source_name}")
  版本号永久单调递增，避免 ES 查询竞争。
```

### 🟡 风险 I-6：`process_and_index` 调用 `splitter.process_document` 两次导致资源浪费

**根本原因**  
第 433 行切片一次，第 501 行又切片一次（双粒度），共两次完整的语义切片流程。对大文档（百页 PDF）其代价是 2x 内存 + 2x LLM 调用。

**根治方案**

```python
# 第一次调用结果直接复用，删除第一次切片

# 删除这行（第 433 行）：
# chunks = self.splitter.process_document(raw_text)

# 保留第 501 行的双粒度切片，直接用其结果：
chunk_sets = self.splitter.process_document(raw_text)
coarse_chunks = chunk_sets.get('coarse', [])
fine_chunks   = chunk_sets.get('fine',   [])
```

## 二、权限管理（Permission Management）

### 🔴 风险 P-1：`listDocs` 接口无用户身份校验 → 全量文档目录泄露

**根本原因**  
```java
@GetMapping("/admin/docs")
public Map<String, Object> listDocs(...) {
    // ❌ 无任何权限前置校验！
    IPage<KbDocRegistry> result = registryService.listDocs(page, size, keyword, status);
    ...
}
```
`/api/v1/admin/docs` 是管理接口（路径语义为 admin），但代码中没有校验身份。任何人只要到达该接口，即可分页枚举出整个知识库的文档目录，包括 PRIVATE/DEPT 文档的名称、版本、上传者姓名等敏感元数据。

**风险等级**：🔴 高（信息泄露）

**根治方案**

```java
@GetMapping("/admin/docs")
public Map<String, Object> listDocs(
        HttpServletRequest request,
        @RequestParam(defaultValue = "1") int page, ...) {
    // P1：校验管理端凭证
    String token = request.getHeader("X-Internal-Token");
    if (!permissionGuard.isValidInternalToken(token)) {
        Map<String, Object> res = new HashMap<>();
        res.put("code", 401);
        res.put("msg", "未授权访问，管理端接口需携带有效凭证");
        return res;
    }
    // 原有业务逻辑...
}
```
长远方案：在 Spring Security 配置中对 `/admin/**` 路径强制要求 ROLE_ADMIN，通过 JWT 解码验证。

### 🔴 风险 P-2：`deleteDoc` 和 `updateMeta` 无权限校验 → 任意文档删改

**根本原因**  
```java
@DeleteMapping("/admin/docs/{id}")
public Map<String, Object> deleteDoc(@PathVariable Long id) {
    // ❌ 无身份校验、无权限校验
    boolean ok = registryService.deleteDoc(id);
    ...
}
```
攻击者只要枚举 id（自增整数，容易猜测），即可删除任意文档的元数据；同样问题存在于 `PUT /admin/docs/{id}/meta`。

**风险等级**：🔴 高（数据破坏、权限越权）

**根治方案**

```java
@DeleteMapping("/admin/docs/{id}")
public Map<String, Object> deleteDoc(@PathVariable Long id, HttpServletRequest request) {
    // 1. 身份鉴权（管理员凭证）
    if (!permissionGuard.isValidInternalToken(request.getHeader("X-Internal-Token"))) {
        return Map.of("code", 401, "msg", "未授权");
    }
    // 2. 操作前校验文档存在且未删除
    KbDocRegistry doc = registryService.getById(id);
    if (doc == null || "DELETED".equals(doc.getStatus())) {
        return Map.of("code", 404, "msg", "文档不存在或已删除");
    }
    // 3. 操作审计日志
    log.info("[DocDelete] operator={} docId={} sourceName={}",
        request.getHeader("X-User-Id"), id, doc.getSourceName());
    boolean ok = registryService.deleteDoc(id);
    return Map.of("code", ok ? 200 : 500, "msg", ok ? "删除成功" : "删除失败");
}
```

### 🔴 风险 P-3：GRANT 权限校验残缺 — MySQL 侧无授权列表，搜索侧与管理侧逻辑割裂

**根本原因**  
`PermissionGuard.java` 第 100-106 行注释已揭示：
```java
case "GRANT":
    // granted_users 暂存于 ES，MySQL 侧暂无独立表
    // 管理 API 场景下 GRANT 类型文档只允许上传者或管理员访问
    if (doc.getUploaderId() != null && doc.getUploaderId().equals(userId)) {
        return AccessResult.allow();
    }
    return AccessResult.deny(...);
```
这意味着：在管理接口中，`GRANT` 类型文档的被授权用户（非上传者）无法通过版本查询 API 访问文档，但在搜索接口中他们可以看到；两条路径权限不一致，属于权限漏洞。

**风险等级**：🔴 高（权限模型不一致，可绕过）

**根治方案**

```sql
-- 在 MySQL 新建授权明细表，作为唯一权威来源
CREATE TABLE kb_doc_grants (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    doc_id      VARCHAR(100) NOT NULL COMMENT '文档 source_name',
    grantee_id  VARCHAR(64)  NOT NULL COMMENT '被授权用户ID',
    granted_by  VARCHAR(64)  NOT NULL COMMENT '授权操作者',
    expires_at  DATETIME     COMMENT '过期时间，NULL=永久',
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_doc_grantee (doc_id, grantee_id)
);
```
```java
// PermissionGuard.canAccess() GRANT 分支改为：
case "GRANT":
    if (doc.getUploaderId().equals(userId)) return AccessResult.allow();
    // 查 MySQL 授权表
    boolean granted = grantService.isGranted(doc.getSourceName(), userId);
    return granted ? AccessResult.allow() : AccessResult.deny("您未被授权访问此文档");
```
ES 中的 `access_groups` 仅作检索过滤的**辅助冗余**，不作为权威来源，每次入库时从 MySQL 同步。

### 🟠 风险 P-4：部门前缀匹配逻辑存在越权风险

**根本原因**  
```java
// PermissionGuard.java 第 89 行
if (userDept.startsWith(docDept) || docDept.startsWith(userDept)) {
    return AccessResult.allow();
}
```
`docDept.startsWith(userDept)` 这一侧的逻辑使得**上级部门用户可以访问下级部门的文档**，这在大多数政务场景中是不合规的（文件向下保密，上级不一定有权查阅下级内部文档）。

例如：文档 `deptCode="620102"`（某区），用户 `deptCode="62"`（省级），`"620102".startsWith("62") = true`，省用户可读区级 DEPT 文档。

**根治方案**

```java
// 精确的访问控制语义：
// 场景 A：文档属于上级部门，下级有只读权限（向下可见）
//   即：docDept 是 userDept 的前缀或相等
// 场景 B（当前存在）：反向也放行，实属越权

// 根据业务明确选择其中之一，一般应为场景 A：
// 即：用户部门是文档部门的下级或同级
if (userDept.startsWith(docDept)) {  
    // userDept="620102" 且 docDept="62"：省级文档，区级用户有权读
    return AccessResult.allow();
}
// 移除 docDept.startsWith(userDept) 的方向，除非业务确有此需求
```
并在设计文档中明确定义"谁可以访问谁"的方向，避免模糊。

### 🟠 风险 P-5：`getVersions` 查找文档的方式性能极差且不稳定

**根本原因**  
```java
KbDocRegistry entry = registryService.listDocs(1, 1, null, null).getRecords()
        .stream().filter(r -> r.getId().equals(id)).findFirst().orElse(null);
```
`listDocs(1, 1, ...)` 只查第一页（仅1条数据），然后用 Stream filter 去找目标 id。当 id 不在第一页时，必定返回 `null` → 404，**这是功能性 Bug**。

**根治方案**

```java
// 直接用主键查询，O(1) 代替 O(n) 全表扫描
KbDocRegistry entry = registryService.getById(id);
```
`KbDocRegistryService.getById()` 使用 MyBatis-Plus 主键查，是正确且高效的做法。

### 🟡 风险 P-6：前端路由缺少导航守卫 → /admin 任意访问

**根本原因**  
```javascript
// router/index.js — 无任何 beforeEach 守卫
const router = createRouter({ history: createWebHistory(), routes })
export default router
```
`/admin`, `/admin/doc-import`, `/admin/tuning` 等高风险管理页面无前端鉴权，任何知道路由的人（或 URL 爆破）直接访问。虽然后端接口有部分校验，但前端无守卫加剧了攻击面（未授权用户可直接操作 UI 触发接口调用）。

**根治方案**

```javascript
// router/index.js
const ADMIN_PATHS = ['/admin']

router.beforeEach((to, from, next) => {
    const isAdminRoute = ADMIN_PATHS.some(p => to.path.startsWith(p))
    if (isAdminRoute) {
        const token = localStorage.getItem('admin_token')
        if (!token) {
            next({ name: 'Home', query: { redirect: to.fullPath } })
            return
        }
    }
    next()
})
```

## 三、混合检索（Hybrid Search）

### 🔴 风险 S-1：`X-User-Id` / `X-User-Dept` 完全信任请求方 → 权限可伪造

**根本原因**  
```java
// SearchController.java 第 87-94 行
String userId = request.getHeader("X-User-Id");
if (userId != null && !userId.trim().isEmpty()) {
    filters.put("user_id", userId);
}
String deptCodeHeader = request.getHeader("X-User-Dept");
if (deptCodeHeader != null && !deptCodeHeader.trim().isEmpty()) {
    filters.put("user_dept_code", deptCodeHeader);
}
```
`X-User-Id` 和 `X-User-Dept` 被直接信任，但代码中没有验证这些 Header 是否来自可信网关（vs 客户端伪造）。若网关未做 Header 重写/剥离，客户端可直接传 `X-User-Id: admin`，以管理员身份检索任意文档。

**风险等级**：🔴 严重（权限完全绕过）

**根治方案**

```
1. 网关层（Nginx/Kong/Spring Gateway）强制剥离来自客户端的 X-User-* 系列请求头，
   仅允许网关在验证 JWT 后自行注入。

2. Java 侧增加 JWT 签名验证（不能仅靠 Header传递）：
```
```java
// 从 Authorization: Bearer <jwt> 中解析，网关签名验证
String jwtToken = request.getHeader("Authorization");
Claims claims = jwtVerifier.verify(jwtToken);  // 签名校验失败则抛出异常
String userId = claims.getSubject();
String deptCode = (String) claims.get("dept_code");
// 将从 JWT 中解析的身份注入 filters，不信任任何来自客户端的 X-Header
```

### 🟠 风险 S-2：`X-Search-AppCode` 是唯一鉴权门槛且验证逻辑不明

**根本原因**  
```java
String appCode = request.getHeader("X-Search-AppCode");
if (appCode == null || appCode.isEmpty()) {
    response.put("code", 401); 
    response.put("msg", "未检测到厂家鉴权码...");
    return response;
}
```
代码仅检查 `appCode` 是否为空，并不验证其有效性（是否在白名单内、是否过期、是否被吊销）。任何人只要填一个非空字符串即可通过鉴权。这个"鉴权"是虚设的安全感。

**根治方案**

```java
// 引入 AppCode 白名单，从配置/Redis/数据库加载（可热更新）
@Autowired
private AppCodeRegistry appCodeRegistry;

String appCode = request.getHeader("X-Search-AppCode");
if (appCode == null || !appCodeRegistry.isValid(appCode)) {
    response.put("code", 401);
    response.put("msg", "无效的厂家鉴权码");
    return response;
}
// AppCodeRegistry 内部维护：appCode → {允许的 IP 范围, 每日限额, 过期时间}
```

### 🟠 风险 S-3：CompletableFuture 超时后原任务线程泄漏

**根本原因**  
```java
results = CompletableFuture.supplyAsync(() -> {
    return searchService.hybridSearch(...);  // 可能耗时 30s
}).get(searchTotalTimeoutMs, TimeUnit.MILLISECONDS);
```
`get()` 超时后当前线程继续执行并返回降级结果，但 `supplyAsync` 内的 `hybridSearch` 仍在 ForkJoinPool 线程中**全速运行**，直到自然结束。如果请求并发量高，超时线程会不断累积，最终耗尽公共线程池（ForkJoinPool.commonPool）。

**根治方案**

```java
// 1. 使用专属线程池（隔离，避免占用公共池）
private static final ExecutorService SEARCH_POOL = 
    Executors.newFixedThreadPool(20, r -> {
        Thread t = new Thread(r, "search-worker");
        t.setDaemon(true);
        return t;
    });

// 2. 在 SearchService 内部支持 Future.cancel → 使用可取消的 ES 请求
//    或者给 CompletableFuture 设置超时取消：
CompletableFuture<List<...>> future = CompletableFuture.supplyAsync(
    () -> searchService.hybridSearch(...), SEARCH_POOL);
try {
    results = future.orTimeout(searchTotalTimeoutMs, TimeUnit.MILLISECONDS).join();
} catch (CompletionException ce) {
    future.cancel(true);  // 尝试取消内部任务
    results = Collections.emptyList();
}
```

### 🟠 风险 S-4：查询日志 JSON 手动拼接 → XSS / JSON 注入

**根本原因**  
```java
String log = String.format(
    "{\"query\":\"%s\",...}",
    query.replace("\"", "'"),   // 仅替换双引号，换行符/控制字符仍可注入
    ...
);
```
`query` 用户输入直接嵌入 JSON 字符串，只替换了 `"` 为 `'`，但未处理换行符 `\n`、回车符 `\r`、反斜杠 `\`、Unicode 转义等。攻击者传入 `\n"result_count":9999,"injected":true`，即可污染日志结构，影响离线分析可靠性，甚至导致下游 SIEM/日志系统解析异常。

**根治方案**

```java
// 引入 Jackson ObjectMapper（项目大概率已有 Spring Boot 自动装配）
@Autowired
private ObjectMapper objectMapper;

private void writeQueryLogAsync(String query, ...) {
    try {
        Map<String, Object> logMap = new LinkedHashMap<>();
        logMap.put("query",        query);       // ObjectMapper 自动转义特殊字符
        logMap.put("appCode",      appCode != null ? appCode : "");
        logMap.put("userId",       userId != null ? userId : "anonymous");
        logMap.put("result_count", resultCount);
        logMap.put("latency_ms",   latencyMs);
        logMap.put("cache_hit",    isCacheHit);
        logMap.put("ts",           LocalDateTime.now().toString());
        String logJson = objectMapper.writeValueAsString(logMap);
        CompletableFuture.runAsync(() -> { ... push logJson to Redis ... });
    } catch (Exception e) { ... }
}
```

### 🟡 风险 S-5：缓存键包含原始 `filters` Map 无确定性顺序 → 缓存穿透

**根本原因**  
```java
String cacheKey = searchCacheService.buildKey(appCode, queryText, topK, filters);
```
`filters` 是 `HashMap`，其 `toString()` 或序列化结果的 key 顺序在不同 JVM 调用间可能不一致（Java HashMap 无序）。同一查询因 filters 序列化顺序不同，产生不同 cacheKey，导致大量缓存 Miss（缓存穿透），Redis 中存储大量重复等效缓存条目。

**根治方案**

```java
// buildKey 时对 filters 排序后序列化
public String buildKey(String appCode, String query, int topK, Map<String, Object> filters) {
    // 用 TreeMap 保证 key 字典序稳定
    String sortedFilters = new TreeMap<>(filters).toString();
    String raw = appCode + ":" + query + ":" + topK + ":" + sortedFilters;
    return "search:cache:" + DigestUtils.sha256Hex(raw);
}
```

### 🟡 风险 S-6：SLA 超时降级返回 HTTP 200（含 `sla_timeout: true`）可能误导调用方

**根本原因**  
```java
response.put("code", 200);
response.put("msg",  slaTimeout ? "success (sla_timeout_degraded)" : "success");
```
超时降级仍返回 HTTP 200，调用方（前端或其他服务）若仅判断 `code === 200` 则认为正常，实际拿到的是空结果。这个行为在分布式系统中会扩散"虚假成功"，使监控报警失效。

**根治方案**

```java
if (slaTimeout) {
    response.put("code", 503);   // Service Unavailable，符合 HTTP 语义
    response.put("msg",  "搜索服务响应超时，请稍后重试");
    // 同时触发告警：向监控系统上报 search.timeout 指标
    meterRegistry.counter("search.timeout").increment();
}
```
