## 2. 实施方案 (Implementation Plan)

为了彻底根治传统 RAG 分块“破坏公文语境”的顽疾并实现您的规范，我们需要在 Python `ai_service` 中自建一套 **【多规制公文级语义解析管线 (Official-Doc Semantic Parser)】**，直接替换掉原本孱弱的 `MarkdownTextSplitter`。

下面是为您量身定制的三步走实施架构：

### 阶段一：重筑实体与解析核心 (Data Class & Pattern Engine)
* **创建 `core/chunking/` 模块：** 彻底独立化切块逻辑，不再污染 RAG 主控制流。
* **定义标准化结构：** 严格按照文档实现 [Chunk](file:///e:/project/AI/knowledge-base/ai_service/core/chunker.py#3-39) 的 Dataclass（包含 `chunk_type`, `section_path`, `quality_score` 等必需字段）。
* **公文特征正则锚点库：** 编写高性能正则，如识别一级大纲 `^[\u4e00-\u9fa5]+、`，二级大纲 `^\([\u4e00-\u9fa5]+\)`，三级大纲 `^\d+\.`，以及文号识别式 `.*〔\d{4}〕\d+号`。

### 阶段二：组装流水线 (The 11-step Pipeline)
我们将开发一个调度类，专门按照您的流程图处理经由 `MarkItDown` 转义出来的干净 Markdown 文本。
1. **A1-A5 (结构解析层)：** 遍历 Markdown 行，遇到特定的正则标题时产生“节点边界”并记录当前的 `section_path` (类似于维护一个栈结构，进入新章节更新路径)。剥离遇到表格语法的行作为独立 `Table Chunk`。
2. **A6-A7 (拼接重组层)：** 对上一步切出的初始块进行大小判定。不足 100 字与相邻块进行指针合并；超过 500 字则利用 `re.split(r'[。；\n]')` 寻找安全断点二次剥茧。
3. **A8-A11 (特征精加工层)：** 对所有处理好的 Chunk 计算滑窗重叠补丁，并执行打分器（计算特殊符号占比、剔除空白块和乱码废块）。

### 阶段三：管道平滑介入与知识树入库 (Pipeline Integration)
* **修改 RAG 入库器：** 将 [rag_pipeline.py](file:///e:/project/AI/knowledge-base/scripts/rag_pipeline.py) 中原来负责切片的 `self.splitter.split_text(raw_text)`，升级为调用 `self.semantic_splitter.process_document(raw_text)`，接收带丰富特征的 `[Chunk]` 对象簇。
* **ES 实体拓展：** 更新 Elasticsearch Mapping，让每一个最终存入的 `Vector Chunk` 附带上它专属的 `section_path`（所处层级：如“第一章/第二节”）和 `chunk_type`。
* **检索时的高阶降维展现：** 这样未来大模型作答时，不仅知道知识点，甚至能直接溯源告诉用户：“这来自于文件的**《第二部分/第四条》**”！

## 💥 深度剖析：该方案的深层缺陷与企业级优化解法 (The Hidden Flaws)

在表面上，按标题层级（A5）、加重叠（A8）、去皮清洗（A11）似乎是一套完美的流水线。但如果我们把大模型在**真实 RAG 召回链路**的底层逻辑（即 Embedding 模型是怎么看这段文本的）拿出来，用第一性原理剖析，就会发现这套 11 步走方案暗藏着 **3 个致命的检索陷阱**：

### 缺陷一：跨层级的“悬空语义失真” (Context Detachment Loss)
**隐患：** 第 A5 步说：“在标题层级处强制切分”。假设一份文件：
> 一、对于新能源车的补贴政策
> (一) 补贴金下发标准
> 1. 对象：仅限纯电动车辆。

在切块时，“对象：仅限纯电动车辆。”因为被强制打断，其最终的切片 `content` 只有区区 10 几个字。即便你在 A10 将它附带了 `section_path: "一/(一)/1"`，**但你存给 BGE 或 OpenAI 向量化模型去算特征向量的依然只是一句没头没尾的“对象：仅限纯电动车辆”**。当用户搜“新能源车补贴去哪领？”，这句话的余弦相似度极低，根本召不出来！

**🔥 登月级优化：向上追溯与文本自愈织入 (Contextual Parent Enrichment)**
* **方案：** 绝对不能只把 `section_path` 存为供人类看的附加字段 (Metadata)！
* 我们在将分片丢给 Embedding 模型去算向量之前，必须将父级标题像面包屑一样**浓缩并主动强插在 Chunk 文本的开头**。
* **效果：** 最终存入向量引擎的原文将变成：`[语境上下文：关于新能源车的补贴政策 > 补贴金下发标准] 正文：对象：仅限纯电动车辆。` 这样这句话的向量瞬间拥有了强烈的“补贴”与“新能源”特征，召回率将呈几何倍数暴增。

### 缺陷二：表格与长尾复杂符号的“高维瞎眼”现象 (The Markdown Table Trap)
**隐患：** A4 说“将表格独立提取为 Chunk”。但如果是包含了几十列数据的 Markdown 表格 `\|年度\|GDP\|增幅...`，大量的管道符`|`和连字符`-`会严重稀释原本具有语义的文字特征。更可怕的是，大多数 1024 维以下的 Embedding 模型（特别是中文模型）对长达几百个 token 的纯数据表格**完全毫无语义理解能力**。你存一个原汁原味的表格，它在向量空间中就像一堆底噪极高的乱码，根本搜不中。

**🔥 登月级优化：表归表、数归数 (Summary Embedding & Raw Context Return)**
* **方案：** 当切到 `chunk_type == 'table'` 时，调用本地的廉价小模型（或特定的统计总结模块），为这个巨大的乱码表格生成一段**概括性文字摘要** (Table Summary)。
* 然后，我们**只把这段通顺顺畅的摘要 (Summary) 去做向量化存入 ES，但在 payload 里暗藏表格的完整 Markdown 源码**。
* **效果：** 当用户问“2023年哪个省GDP最高？”，大模型引擎能通过自然语言的 Summary 瞬间击中该片段，然后再把完整的 Markdown 表格源码投喂给 LLM，如此既保障了检索的精准命中率，又保障了大模型幻觉的零容忍（能读懂源码）。

### 缺陷三：“无脑50字重叠”导致的严重语病斩断 (Brainless Overlap Slicing)
**隐患：** A8 里面写着“取前一个 Chunk 结尾 50 字加到开头”。在真实长文切块（如以 500 字一分为二的报告）中，前一个块的最后 50 字很可能正好卡在一句话的中间。
*例如：前一块结尾50字是：“...综上所述，因为大模型具有广泛的可迁移”。下一块开头是：“能力，所以我们在农业也部署了它。”*
你强行抓 50 个字，会导致大模型在读第二个块时看到：`广泛的可迁移能力，所以我们在农业也部署了它。`，这造成了极大的语义割裂和病句特征，拉低向量质量。

**🔥 登月级优化：动态语义锚点后退 (Dynamic Sentence-Boundary Lookback)**
* **方案：** 摒弃粗暴的“固定前取 50 字符”。
* 必须在代码中维护一个标点符号扫描器。当需要重叠时，往前回溯直至遇到第一个完整的“语义终结符（如 `。`或`！`或者`\n`）”。将**上一个完整的句子集合**作为重叠窗口补充到下一段。
* **效果：** 每一个 Chunk 的开头，必定是极其标准且通配的自然句起手，没有任何截断式语病，保障了 RAG 上传语境的 100% 顺滑。

## ⏱️ 1秒极限检索挑战：性能评估与参数调优下沉方案

针对您在“现有系统结合”与“1秒延迟红线”中提出的顾虑，对 11 步语义切块进行如下工程化架构评估：

### 1. 调优参数的无缝下沉对接 (Parameter Dynamic Integration)
《语义分片.md》中定义的 7 大关键阈值（如 `max_chunk_size`, `overlap_size` 等）**完美兼容现有的 SysAiTuningConfig 热更新架构**。
* **链路设计**：在 Java `sys_ai_tuning_config` 表中追加对应的 JSON 列，在 Vue 前端的 [ModelTuning.vue](file:///e:/project/AI/knowledge-base/frontend/src/views/admin/ModelTuning.vue) 界面补充“语义分片参数矩阵”拖动条。后端将这些参数透传至 Python [cfg](file:///e:/project/AI/knowledge-base/ai_service/venv/pyvenv.cfg) 字典。
* **热效机制**：由于所有的公文结构化拆解发生在**进件期 (Upload Indexing)**，您可以在 Vue 上动态调整重叠窗口字数，一旦点击保存，下一秒任何人上传的任何新公文，都会严格遵从新参数域进行精准切割，做到 100% 动态挂载！

### 2. “1 秒检索红线”损耗分解评估 (Full-Path Latency Breakdown)
复杂语义切分让库内碎片数激增（对比原先可能暴涨 1.5 - 2 倍的总 Chunk 量）。在**查询 (Query) 阶段**的链路耗时全量预测：
1. **BGE-M3 Query 嵌入计算**：约 `~20-40ms`。
2. **ES HNSW/KNN 检索前 50 碎片**：倒排及向量检索引擎完全不受百万级以下碎片的绝对数量惩罚，固定耗时 `~30-80ms`。
3. **⚠️ 风险瓶颈：Reranker 重排矩阵运算**：如果我们强行要求大参数的交叉重排库 `BGE-Reranker-Large` 去精算这暴增的 50 条携带面包屑重叠上下文的 Chunk，由于其复杂度为 $O(L^2)$，在常规算力池中可能暴拉至 `600ms - 900ms`，甚至破秒！
4. **VLLM 发送提示词组与首字吐出 (TTFT)**：约 `~200ms - 400ms`。

**评估结论：如果您指的是“检索结果并用大模型开启回答”，当前的纯物理叠加方式在无降级机制下，将有极大踩破 1 秒查询底线的风险！**

### 3. 为保底“1秒”的极端性能降级优化 (Sub-Second Survival Mechanics)
为了让拥有“父级级联注入”和细碎切片的顶级感知能稳固运行在 1 秒线内，我们**必须**落地以下三大短路策略：

#### 🚀 优化一：Reranker 智能短路熔断 (Dynamic Top-K Pruning)
* 在进行耗时的全局重排序前，检测 ES 抛出的原生向量 `score`。
* 若第一名的原始余弦分数已高达 `0.85`（说明完美对冲语义，无需猜疑），业务层直接放弃 `Reranking` 跳出流水线。
* 若命中模棱两可，强制在代码里对送进 Reranker 的池大小从 Top-50 **熔断切片至 Top-10**，用极小的数据量换掉巨大的推理开销，牢牢将重排时间按死在 200ms 以内。

#### 🚀 优化二：入库阶段拒绝大模型“摘要生成” (Regex Dehydration vs. LLM)
* 在对缺陷二中复杂的表格或乱码特征进行清洗时，**绝对禁止**调用大语言模型去异步总结。我们必须退而求其次，在 Python 层编写极致轻量的“正则矩阵脱水器”，把 `|A|B| 行1...` 纯 CPU 操作直接转储为一行压平的 `表头A:行1键值` 结构。确保存入和召回全是 0ms，让任何表格都能极速在特征空间穿透。

#### 🚀 优化三：LLM 强制流式吐字协议 (SSE Forced Response)
* 搜索引擎一旦圈定好最终结果（整个查找开销约计 300ms 以内），在请求大模型回答时，强制切换所有后链路以 HTTP Server-Sent Events (SSE) 持续推流。只需确保首个字符突破网络在 600ms 以内落入前端 `v-model` 流中，用户的体验即为“即时响应”，打破心理界限。
